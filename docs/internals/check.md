# `ossprey check`

Why `check` reads a package spec the way it does. [Back to the internals index](README.md).

**`check -e <pypi|npm|cargo> <name[@version]>...`** checks named packages with no project on disk. A crate takes one exact release or none (`splitCargo`: the version after an optional `=` is held to `registry.IsCargoRelease`, the release grammar the cataloguer applies after its required `=`, and the name to `registry.IsCargoName`; a bare `1.2.3` is that exact release, as `cargo install` reads it): Cargo reads `1.0` as a caret range and nothing here resolves a cargo range, so a range is an error rather than a check of a guessed release; a bare name resolves the latest stable release from crates.io. Both forms go through `registry.CanonicalCrate` and are sent under crates.io's own spelling, because crates.io folds case and `-`/`_` into one crate while the malware lookup matches the name exactly; an outage is an error, but a pinned crate crates.io answers 404 for is sent as typed, since crates.io deletes malicious crates and those are the ones most worth checking. The service folds crate names only for package-wide verdicts, so a deleted crate typed in another spelling still meets one, while a per-version record matches the name exactly. Cargo itself never folds a spelling (verified with cargo 1.99.1: `serde-json = "=1.0.100"` fails with no matching package), so a `Cargo.toml` that builds names each crate as crates.io spells it, and the pre-commit hook sends that spelling unchanged.
