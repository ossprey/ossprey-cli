# Named-install and tool-run expansion (OSS-2481)

How `resolveNamed` works out what an install or tool run would add, and every case where the dry run has to be told what the real command reads. [Back to the internals index](README.md).

**A named install is checked with its dependencies (OSS-2481).** `npm install express` installs 65 packages; the forwarder used to check one, and the planted package in a real attack is rarely the one asked for. `resolveNamed` (`internal/forward/expand.go`) asks the manager's own kind of resolver what the install would add — `catalog.ResolveNpmInstall` runs `npm install --package-lock-only --ignore-scripts` in a throwaway copy of the project; `catalog.ResolvePythonInstall` runs `uv pip compile --no-build`, or `pip install --dry-run --only-binary=:all:` without uv — and checks the whole tree at the releases the resolver picked. Four rules: it **never runs package code** (no scripts, no sdist builds; a package that needs building fails the dry run and falls back); it **fails open, out loud** — on any error the names are checked alone and `reportUnexpanded` prints one line even when quiet, since a clean verdict on the names must not read as a verdict on the install (a tool run's cached or installed trees, below, are read whether or not the dry run succeeds — a failed resolution is exactly when npm reuses its npx cache — and come back beside the error, so `resolveNamed` still counts them and the line claims them: `checking the named packages and N dependencies from an earlier run`; and since such a tree says nothing about what resolves today, the names are then resolved as well — `npx tool@latest` with `tool@1.0.0` cached may fetch `2.0.0` — each counted once and a release already in the set not repeated, and a cached copy's trusted provenance covering that copy only, never the lookup); the npm copy is **diffed against the project's lockfile** (`Resolved.Locked`), so only what the install adds is checked, not a monorepo's thousand locked packages; and the copy drops local/workspace deps so npm resolves from registries alone. The scratch dry run is **isolated from whatever is above it**: with no project it gets a minimal `package.json` of its own, since npm otherwise takes the nearest ancestor with one as the project and rewrites that project's `package.json` and lockfile (verified: a `TMPDIR` inside a project did exactly that), and every dry run passes `--workspaces=false` so npm cannot walk on to an ancestor workspace root whose globs name scratch (a copied root still locks its own members, verified); the uv probes (`uv cache dir`, `uv tool dir`) name their configuration through `uvToolRunConfig` for the same reason, since a bare scratch directory does not stop uv discovering a project's `uv.toml` above it. The project is the context only when the install will update a lockfile npm can read (`npmProjectDir`); otherwise the names resolve on their own. Trust applies to the tree with the registries the resolver reported. Resolvers get the tokens as typed (`installArgs.Tokens`), and only resolution-affecting flags (`pickFlags`). Tool runs (`npx`, `npm exec`, `bunx`, `uvx`) are expanded too (`installArgs.ToolRun`): with no project context, since the package goes into the tool's own cache, and with none of the program's argv read as a resolver flag — only a uvx flag before the command (`toolRunLeadingFlags`, translated for the pip fallback by `toolRunPipFlags`) reaches the Python resolver, and only the `--registry` and `--userconfig` npm's own parse attributes to npm (`npmArgv.Registry`/`Userconfig`, the path made absolute since the dry run runs elsewhere) reach the npm one. A uv command with a flag pip cannot honour (`uvOnlyResolution`: `--index`, `--extra-index-url`, `--overrides`, `--resolution`, `--exclude-newer`, `--torch-backend`, `--no-binary` — pip's dry run is `--only-binary=:all:`, so it would pick the newest release with a wheel where uv builds the newest of all — …) never reaches the pip fallback: uv takes the first index that has the package, pip the best version across indexes, so pip would check a release uv does not install, and a private-only name would resolve from PyPI, where a squat may wait. `needsUV` routes it to `catalog.ResolvePythonInstallWithUV`, which fails with `ErrNeedsUV` on a host without uv so the names are checked with the warning (`TestExpandInstall_UVOnlyFlagsAreResolvedByUVOnly`). The same holds for configuration outside the line (`catalog.UVConfigShapesResolution`): a `UV_INDEX_URL` or any other `UV_*` variable for an index, strategy, cut-off, build policy, interpreter or override, or such a key (or a `[pip]` table with one) in the file uv reads — `--config-file`/`UV_CONFIG_FILE`, else the project's `uv.toml`/`pyproject.toml [tool.uv]` for a named install (never for a tool run), and the user- and system-level `uv.toml`, which uv merges underneath a project file, so a project file that shapes nothing stops discovery above it and not their check — makes the command uv-only, since pip reads none of it and would resolve from the public index instead; an unreadable file counts as shaping, and `--no-config` stops the files but not the variables. `--default-index` still maps to pip's `--index-url` and `--constraints` to `--constraint`, which mean the same. A uv config named as a pipe (`--config-file <(...)`, `UV_CONFIG_FILE=/dev/fd/3`) is never opened by the dry run or the probes (`uvConfigPipe`): a pipe is read once, uv's children inherit the fd (verified), so any read before the run leaves uvx an empty config and the default index, and the names are checked alone with a line naming the file as a pipe.

**Configuration follows the real command, not the cwd.** uvx reads no project configuration (verified: a `uv.toml` with a bad index breaks `uv pip compile` in that directory and not `uvx`), so a tool run resolves with `dir ""`, a scratch directory, and `pythonPathFlags` are made absolute first. The `[pip]` table is the other way round: `uv pip compile` applies it and uvx ignores it (verified: one file with a top-level `index-url` and a `[pip] index-url` sends uvx to the former and the compile to the latter), so for a tool run `uvToolRunConfig` writes the configuration the run reads — the file named by `--config-file` or `UV_CONFIG_FILE`, else the user-level `uv.toml` merged over the system-level one as uv merges them (`mergeTOML`: table by table, the user's value winning, and arrays joined with the user's entries first — verified with `--show-settings`, where the user's `[[index]]` and `extra-index-url` entries precede the system's — since replacing the array dropped an index the run uses) — into scratch without that table and names the copy with `--config-file`, with every relative local path among a file's index and find-links settings made absolute against that file's directory first (`anchorUVConfigPaths`), since uv resolves them there and not against the cwd (verified: `find-links = ["./wheels"]` in the user-level file reads `<config dir>/wheels` from any directory and under `--directory`), so the copy in scratch would otherwise send the dry run to directories under scratch and resolve from the registry what the run takes from local wheels; always, when the files are discovered rather than named, even with no table or no file at all (an empty one then), since a named file stops uv discovering a project's `uv.toml`/`pyproject.toml` above scratch (verified), and scratch sits under a project when `TMPDIR` points inside one; `UV_CONFIG_FILE` names configuration pip does not read, so `uvEnvConfigFlag` hands the resolver and the probes `--config-file <abs>` whenever it is set (absolute or not), which makes the run uv-only rather than letting the pip fallback resolve from indexes the run does not use, and a relative value is made absolute first since it is read where the run runs (`uvToolRunConfig` does the same for a direct caller, even without the table, since the resolver runs in scratch where uv would not find it); **An npx run may execute a tree resolved earlier**: npm keeps each tool run's installation under `<cache>/_npx/<key>` (`key` = the first 16 hex chars of sha512 of the sorted `--package` values, else the command, joined by newline — `catalog.NpxCacheKey`, `TestNpxCachedTreeMatchesARealRun` holds it to a real npx) and reuses it when the package there still satisfies the request, with the dependencies resolved back then. So `withNpxCached` unions the fresh dry run with that cached lock (`catalog.NpxCachedTree`), and an unreadable cache adds nothing. The cache is `--cache`, else `npm_config_cache`, else what npm says with the command's own config-file and location flags (`catalog.NpmConfigGet` with key `cache`, which reads `npm config list -l` rather than `npm config get cache`: the latter refuses a relative path as protected, verified, while the listing prints it resolved against the cwd; a `cache=` in a project, user or global `.npmrc` is where npm reuses from, and the default lookup would miss it), else the platform default when npm cannot be asked. That is one more subprocess per tool run with no `--cache`, next to a dry run costing seconds. It is found once per tool run and handed to `withNpxCached`; and since nopt resolves a relative `npm_config_cache` or `.npmrc` `cache=` against the directory npm runs in, the dry run in scratch is told it absolutely (`npmCacheDir` reports such a path as `moved`; a named install's dry run gets `npmEnvCacheFlag` for the variable), or an offline dry run would face an empty cache. A release both trees report is **one sighting merged conservatively** (`unionSightings`, keyed as the registry compares names — PEP 503 for PyPI, the spelling for npm, where `lodash.get` and `lodash-get` are two packages a PyPI key would fold into one and drop from the check — and `resolveNamed`'s own dedup keys the same way, `canonicalSpec`, so a cached environment's `Django 5.0` and the registry's `django 5.0` are submitted once; `mergeSighting`): a kind survives only when both carry it, the registry only when both agree — a fresh fetch from a trusted registry must not cover a cached copy fetched publicly, and no registry means checked — and the lock covers it only if both say so. Both `npm exec` and the `npx` binary take this path (`m.Bin` is `npx` for the latter, which the first revision missed); bunx has its own cache. The omit policy prunes the **fresh** tree only, before the union: npm reuses a cached installation as it is, so an optional dependency it holds runs under `--omit=optional` too. It prunes npm's and npx's trees only: bun reads none of npm's configuration, so a bunx run installs what an `.npmrc` `omit` would have npm leave out, and pruning it dropped packages that run. The key sorts the specs as libnpmexec does, with node's `localeCompare('en')`, which is not byte order: ICU puts punctuation before digits before letters (`_` before `-`, so `is_js` sorts before `is-odd`) and lowercase before uppercase, and a byte-order key for `--package a_b --package a-b` looked up an entry npm never wrote. `npmCollate` ports that for printable ASCII (primary weights from `npmCollateOrder`, case as a tiebreak) and `TestNpmCollateMatchesNode` holds it to the installed node; `TestNpxCachedTreeMatchesARealRun` finds a real two-package run under it. **uv does the same with tool environments**: `uvx`/`uv tool run` reuse an environment cached under `<cache>/environments-v2/<key>/<key>` (a venv) when it satisfies the request, with the dependencies resolved back then, and `uvx tool@latest` exists because an unpinned request would otherwise never see a newer release. The key is uv's own hash of the request, so `catalog.UVCachedTree` reads every cached environment holding the named packages at the pinned versions (from each dist-info `METADATA` in its site-packages; `lib/pythonX.Y` or `Lib` on Windows; `holdsNames` lists the dist-info directory names first and reads metadata only in an environment that has every wanted name, since a cache holds hundreds of environments and most hold none of them) and `withUVCached` unions them with the fresh resolution, erring toward checking. The cache is `--cache-dir`, else `UV_CACHE_DIR`, else `uv cache dir` (`catalog.UVCacheDir`, one fast subprocess) asked with the run's own `--config-file`/`--no-config` (`uvCacheSelectors`: a `cache-dir` in an explicitly named file is where uvx reuses from, verified) and **from a scratch directory**: uvx reads no project configuration, but `uv cache dir` in a project whose `uv.toml` names a `cache-dir` answers for the project (verified: uvx ignored that file and `uv cache dir` reported it), so asking from the cwd would name a cache the run never touches. Else the platform default, uv's documented one (`uv help cache dir` / `uv help tool dir`): `$XDG_CACHE_HOME/uv` or `~/.cache/uv` on macOS and Linux alike — not `os.UserCacheDir`, which is `~/Library/Caches` on macOS — and `%LOCALAPPDATA%\uv\cache` on Windows; tools under `$XDG_DATA_HOME/uv/tools`, `~/.local/share/uv/tools`, or `%APPDATA%\uv\data\tools`. Every relative path — `--cache-dir c`, a relative `cache-dir` in a config file, which uv resolves against the directory it runs in and not the file's, and so uv's own relative answer — is resolved against `uvDir`'s base, since `uvx --directory sub --cache-dir c` uses `sub/c` (verified). `--no-cache`/`-n`, `--refresh` and `--reinstall` read or rebuild nothing, so they add nothing. A venv records no provenance, so nothing read there is trusted by registry; `TestUVCachedTreeMatchesARealRun` finds a real `uv tool run`'s environment.

**An installed tool is run as installed**: for a bare request — the command or `--from` with no version, no `@latest`, no `--with`, no `--isolated` (each verified against uv 0.11 to make uvx resolve instead) — uvx runs the environment `uv tool install` keeps under `uv tool dir` (`<dir>/<name>`, a venv) and resolves nothing, so `parseToolRun` records `installArgs.InstalledTool` and `withUVCached` unions that environment too (`catalog.UVInstalledTree`, the directory from `UV_TOOL_DIR`, else `uv tool dir`, else the platform default), whatever the cache flags say, since those govern the cache and not installed tools. The npx cache is read the same way: its lock records what the earlier run resolved, omitted dependencies included, so `parseNpmLockAt` keeps only entries whose directory exists under the cached install (a run is not blocked on a package it never put on disk), and reads the whole lock only when there is no `node_modules` to check against. A pin is matched as PEP 440 reads `==` (`pep440Equal`: `6.1.0` is `6.1`, `1.0-alpha1` is `1.0a1`, `+build.01` is `+build.1`, a local segment on the candidate is ignored unless the pin names one), and a spelling the specification does not describe is retained rather than skipped; the site-packages glob is relative to the environment (`fs.Glob` over `os.DirFS`), since a bracket in the cache path would otherwise read as a character class and an existing environment would match nothing. An npm lock entry without `resolved` (npm's `omit-lockfile-registry-resolved`) is kept with no registry — `parseNpmLock` drops only the root, `link` entries and local packages outside `node_modules/` — because a package npm installed from a registry it did not name is one to check, not to drop. An npm lock's alias entry (`node_modules/renamed` with `"name": "left-pad"`) is read by its `name`, the registry package; `--prefix`, `--globalconfig` and `--cache` take nopt's path type, so `~/` is expanded (`expandHome`) before they are made absolute. `TestNamedNpmInstall*`/`TestNamedPipInstall*` in `test/smoke` prove it against real tools; unit tests stub `expandFn`.
